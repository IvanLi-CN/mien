# ADR-0005：有头优先的显示策略

- 状态：已接受
- 决策范围：Docker 显示环境、无头模式定位、noVNC 边界

## 背景

Docker 服务端没有桌面环境，但指纹浏览器的价值主要来自有头浏览器行为：窗口、屏幕属性、图形栈、字体与渲染路径更接近真实用户环境。fingerprint-chromium 的 README 明确说明无头模式只替换了 UA 中的 `HeadlessChrome`，其他 Headless 特征没有改变。若默认使用无头模式，产品会在最关键的指纹一致性上主动降级。

同时，服务器上运行有头 Chromium 需要虚拟 X 服务器；每个档案独立 Xvfb 会显著增加资源开销，共享 Xvfb 又会让所有档案看到相同屏幕尺寸。需要明确默认值和限制。

## 决策

- Docker 默认使用有头模式：Xvfb 提供虚拟显示，openbox 提供基本窗口管理，Chromium 以正常有头方式启动。
- 默认显示为 `1920x1080x24`，通过环境变量配置；所有档案共享该显示。档案只能控制窗口尺寸，不能控制 `screen.width` 或 `devicePixelRatio`。
- noVNC 与 x11vnc 作为可选查看器，默认关闭；开启时使用一次性令牌或独立认证，且只绑定容器网络，不默认暴露到公网。
- 无头模式在桌面与服务端都可选，但必须显式启用，UI 与 API 标记“降低保证”，不得作为默认值。
- macOS 桌面使用宿主桌面有头运行；macOS 无头模式同样标记降级。
- 不安装完整桌面环境；只使用 Xvfb、openbox 和必要的 X 工具，保持镜像小、攻击面低。
- 后续版本可以评估每档案独立 Xvfb 或虚拟显示池，但首个发布不实现。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 默认无头 | 资源低、启动快、无需 Xvfb | 指纹保证明显下降；与产品核心价值冲突 | 不采用 |
| 完整桌面环境 | 行为最接近真实桌面 | 镜像大、攻击面大、维护成本高 | 不采用 |
| Xvfb + openbox 共享显示 | 有头行为；资源可控；实现简单 | 所有档案共享屏幕尺寸 | 采用 |
| 每档案独立 Xvfb | 可独立控制分辨率 | 内存与进程开销高；调度复杂 | 后续评估 |
| 默认开启 VNC | 方便人工查看 | 高权限入口；认证与网络暴露风险 | 不采用 |

## 后果

- Docker 镜像必须包含 Xvfb、openbox、字体和 Chromium 运行库；启动时间与内存高于纯无头。
- 所有档案的 `screen.*` 相同，跨档案屏幕指纹差异只能来自窗口尺寸和内核其他字段；这是产品必须展示的限制。
- noVNC 是可选高权限入口，必须默认关闭并受 Token 保护；容器编排不应直接把它发布到公网。
- 无头模式仍需完整的代理、隔离和进程监督，只是显示与部分指纹保证降级。
- 有头模式在无 GPU 的容器中使用 SwiftShader 或软件渲染；WebGL 元数据由内核伪装，但渲染结果可能与真实 GPU 不同，测试需覆盖。
